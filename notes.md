## Log

- 2026-10-08: v0.11: **own texture pack**. A standalone `.tpk` loads through the game's resource loader: `LoadResourceFile(name, type, flags, callback, param, offset, size)` 0x661760 (cdecl; returns `ResourceFile*`, `LoadingFinishedFlag` at +0x30), advanced by `ServiceResourceLoading()` 0x6626B0 (the symbol map calls it `WaitForResourceLoadingComplete`; the real Wait is 0x662770). `GetTextureInfo(hash, return_default, include_unloaded)` 0x503400 says whether a texture is registered. The pack header's FilenameHash is bHash of its filename (e.g. `INGAMETEXTURES.tpk` = 0x5FE62B91); the 32-bit texture format entry is `{0, 0, 1, 5, 6, 21 (D3DFMT_A8R8G8B8), 0, 0}`. Options icons are 256x256 with a single mip. The Options entry's icon was also being reset to the tuning icon right after creation (`FEngSetTextureHash` on the returned image); v0.11 uses one icon for the entry and the screen header.

- 2026-10-08: v0.10 findings. **Menu textures**: the pause-menu Options icons (`OPTIONS_ICON_*`, 256x256 DXT3/5) are in pack `INGAMETEXTURES` in `GLOBAL/InGameA.bun`; the main-menu copies are in `FRONTENDTEXTURES` in `FRONTEND/FrontB.lzc`, which isn't loaded in-game. `GLOBALTEXTURES`/`GLOBALTEXTURESPC` in `GLOBAL/GlobalB.lzc` are always loaded; the PC key glyphs live there, and so does `MILESTONE_SPEEDTRAP` (0x66C9A7B6, a camera icon). `GLOBALB.BUN` has 64x64 versions of the same hashes. Texture debug names are cut at 23 characters, so the bHash of the visible name can differ from the real hash (e.g. `INGAME_ICON_PERFORMANCE` = 0x483238FD). TPK layout: `0xB3300000` { `0xB3310000` { `0x33310001` header (name at +4), `0x33310004` TextureInfo[0x7C] (name +0xC, hash +0x24, placement +0x30, palette placement +0x34, size +0x38, w/h +0x44, comp +0x4A: 0x22/0x24/0x26 = DXT1/3/5, 0x20 = BGRA) }, `0xB3320000` { `0x33320002` data, aligned to 0x80 } }. WidescreenFix loads standalone `scripts/buttons-*.tpk` files and XenonEffects loads `GLOBAL/XenonEffects.tpk`, so a mod can ship its own texture pack. The Options screen's header icon is object 0x08007B4C (`FEngSetTextureHash(pkg, obj, tex)` 0x527EE0). **Drift camera name**: NFSMWExtraOptions' `EnableHiddenCameraModes` extends `PODriveCam::Draw` (0x51C910) with code caves that use language hash 0xA1211428 ("DRIFT"); the game also has 0x6AEB7EE6 ("Drift").

- 2026-10-08: v0.9.1 apply semantics. The game's options screens edit live and keep `Original*Settings` copies: `OptionsDidNotChange` (0x510360) decides whether Back asks "discard?", a confirmed discard calls `RestoreOriginals` (0x510450), and Accept just leaves (both paths end in `FEHASH_EXITCOMPLETE` 0xE1FDE1D1 on the screen). The camera screen mirrors that: edits stay in memory (`g_ovr`), `g_ovr_open` is the snapshot from screen open, both functions are hooked to include the camera values, and the ini is written on EXITCOMPLETE only if something differs from the snapshot (after a discard they are equal, so nothing is written).

- 2026-10-08: v0.9 findings. **Hint label hover** is driven by script events, not responses. The hit-box's mouse-over script `02EE84A3` is restarted every frame by the 0xB30D0683 "mouse over" response (`MR_SetScript` resets CurTime), and its t=0 event posts 0x696851AD (label HIGHLIGHT). The mouse-exit response runs script `0xCCFA`, whose event posts 0x1C8E4190 (UNHIGHLIGHT). Both events target 0xFFFFFFFC (the whole package), which routes them through the package's message target lists (`Mt` chunks: 0x696851AD/0x1C8E4190 -> GUID 0xfa159, the Defaults label). So a cloned hint must point those events at its own label by GUID (FEScript events: count +0x24, array +0x28 of {EventID, Target, tTime}; FEObject scripts list at +0x44, count +0x48, head +0x4C). **Row label alignment**: `FEStatWidget::Position` centres a label on the column edge using the width of its literal text (`FEngSetCenter` measures `GetString()`, not the language-hash text). Labels set with `FEngSetLanguageHash(FEString*, hash)` (0x515C00) measure as empty and end at the edge (right-aligned). Labels set with `FESetString` get centred.
