# Split screen (nfsmw_split_screen_support)

Input for player 2: see [input-system.md](input-system.md) (extra device). Marks: [read] [tested].
The parts of the mod and their ini switches: the header comment of `Mods/split_screen_support/src/main.cpp` and `nfsmw_split_screen_support.ini`.

## What the PC exe still has
- The console split screen: `UIQRMainMenu::Setup` 0x7AA730 adds only Quick Play (icon 0xE6313967) and Custom Race (0x2A49B5E2), but `NotificationMessage` 0x7A2E20 still handles
  `QRMode` (0x9B9E68) == 2 (player count byte = 2, flag 0x400 in `[FEDatabase+0x12C]`, then the mode select screen). The Split Screen icon (0xF365B5F5, FrontB.lzc) and name (0x841D518A)
  exist in the data. The entry is added by redirecting the call of `IconScrollerMenu::AddOption` 0x573960 at 0x7AA81C (the one that adds Custom Race; not a hook on AddOption, which `nfsmw_custom_menus` hooks and two plugins enabling a hook on one function at start-up can overwrite each other's [guess]) to a function that calls AddOption and then adds an `IconOption` (0x4C bytes, `operator new` 0x652AD0,
  ctor 0x586FA0 (texture, name, description)) whose vtable is Custom Race's (0x8B7590: deleting dtor, React) with React replaced (message 0x0C407210 pressed: QRMode = 2) [tested].
- **FEDatabase** (pointer 0x91CF90): byte 0 player count, `+0x0C/+0x0D` joystick port of players 1/2, `+0x12C` bit 2 = Quick Race. `IsSplitScreenMode` 0x469120 = bit 2 and count 2.
  `Sim::Init` 0x6FC3A0 (from `BeginWorldLoad` 0x662950) gets user mode 1 for split screen (`Game_IsSplitScreen` 0x605630 reads `[0x988E04]`).
- The three fixes (the same ones NFSMWExtraOptions' `ExperimentalSplitScreenFix` makes; GPL source in `Tools/OtherMods/nfsmw-extra-options`, nothing copied): `0x7A3F68` 0x0C to 0x0D (the Press Start
  screen compares the pressed port with `[db+0x0C]`; player 2 may press Start with player 1's device), `0x666EB3` 75 to EB (`TrackLoader::LoadHandler` takes the normal loading screen: the split
  one crashes), `0x6CFC03` NOP (`MaybeChangeViewMode` 0x6CFAD0 only knows modes 0-2; mode 0 switches every view off: the black screen). Ours: byte patches plus a stub for the view mode
  (`common/patch.h`), each with an ini switch, backing off when ExtraOptions' fix is on.

## Rendering
- Other mods can draw into each player's picture: `view_api.cpp` keeps the callbacks registered through the export `nfsmw_split_screen_support_on_view_draw` (`common/split_screen_api.h`) and `split_view.cpp` calls them after each `___eDisplayFrame` (player 0, then player 1 with its view in view 1's place), or once per frame as player 0 when the screen is not split. `nfsmw_improved_ai_opponents` uses it for its overlay and as its per-frame tick.
- **eViews** at 0x9195E0, 0x70 bytes each: `+0` PlatInfo, `+4` id, `+8` Active, `+0x40` camera, `+0x44` mover list, `+0x5C` lighting context (from `SetupWorldLightContext` 0x5029F0, needs only the
  camera), `+0x60` render target. EVIEWMODE (`[0x982B40]` current, `[0x982B44]` requested, `[0x982B3C]` wanted): 3 = two views. View 2 is never Active on PC (its render target is never set); we
  give it view 1's render target and set Active at world load of a split screen game, and off afterwards [tested]: the game then does the per-view setup (0x6CF400: projection from the camera
  and the target) and the streaming for it.
- `eDisplayFrame` 0x6E7220 per frame: per-view setup, BeginScene, lights for views 1-3, **`___eDisplayFrame` 0x6DE300 (the whole world + effects, hard-wired to view 1, 0x919650)**,
  `FEManager::Render` (menus, HUD), EndScene, Present. The game clears colour and depth once per frame, after Present. `split_view.cpp` runs `___eDisplayFrame` twice in mode 3: view 1, copy a
  half-height band of the back buffer into a canvas (top), clear screen and depth, swap view 1 and 2's PlatInfo / camera / lighting (+0 / +0x40 / +0x5C), run again, copy the band (bottom), swap
  back, StretchRect the canvas to the back buffer. The canvas is released in an `IDirect3DDevice9::Reset` hook (vtable slot 16).
- **What a view is, for the second pass** (swapped between view 1 and 2 around the second `___eDisplayFrame`): PlatInfo `+0`, camera `+0x40`, lighting `+0x5C`, and the **camera mover list** (`+0x44`, the head node of
  an intrusive circular list: every node points back to it, so the lists are swapped node by node). `eView::GetCameraMover` is the list's first node. Car rendering asks it: `CarRenderConn::OnRender` skips the car
  the mover follows when `RenderCarPOV` is false (bumper / hood views) and, for the cube-map views, skips the car of view 1's mover. Without the swap player 1's bumper view hid player 1's car in player 2's picture [guess,
  untested fix].
- **Frame memory** [tested]: the game's per-frame pool (current pointer 0x915F84, end 0x915F88; `eSwapFrameMallocBuffers` swaps two of them each frame) is sized for one drawing of the world; the allocator returns null when it is full, and `RenderTextureHeadlights` 0x738180 then crashed in `bMatrixCopy` (flares and headlights of many cars; the second pass also left cars invisible for player 2 at the start). `split_view.cpp` puts the pointer back to where the first pass began before the second.
- **Crash in `CarRenderInfo::Render` on a missing wheel model** [tested: access violation at 0x501640 reading 0xC, split screen race, shadow map pass; fix untested]: the rim code (decomp `CarRender.cpp` ~3430) calls `front_tire_models[i]->GetModel()->ReplaceLightMaterial(MAGSILVER / MAGCHROME / MAGGUNMETAL)` after testing the *address* of the `CarPartModel` (never null), not the model. `RenderPart` handles a missing level (`IsLodMissing`, draws a stand-in), so a wheel or spinner model that is not loaded at `tire_lod` is an expected state and the call crashes with `this` null. `fixes.cpp` hooks `eModel::ReplaceLightMaterial` 0x501640 and skips a null model. Why the model was missing is unknown [guess: the tire level chosen for the second pass's view is one the car has not loaded].
- **With the widescreen fix** [read]: its FOV patch at `eView::SetupPerView` 0x6CF4EA corrects the projection's aspect only for view ids 1 and 4 (the game treats 1, 2, 4, 5 alike there); view 2 would be stretched, so `split_view.cpp` gives view 2 the id 4 during that call when the place is patched. It also hooks `Minimap::AdjustForWidescreen` 0x5678A0 (a jump at its start): the minimap hooks accept that and go on top of it.
- **Reflections**: the car reflection is a cube map drawn from six extra views (18-23 on PC), pointed at view 1's followed car once per frame by `UpdateEnvironmentMapCameras` (0x756060, only when `[0x9017B8]`) and set up by
  `SetupPerView` in `eDisplayFrame`'s loop; `___eDisplayFrame` draws them before the world. For the second pass both are done again after the swap [tested].
  **"Car Reflection Update Rate" is `[0x9017B8]`** (1-3; 0 = off; `g_CarEnvironmentMapEnable`; `[0x9017BC]`, `g_CarEnvironmentMapUpdateData`, only picks the scenery flags for the cube faces): `eEnvMap::UpdateCameras` 0x6DA350 sets each face view's Active byte (+8) from a schedule table (0x8F9028, 6 flags a row) by `[0x982B78]` (frame counter) modulo the period table (0x8F901C: 6, 4, 1): rate 1 one face per frame, rate 2 three faces per 4 frames, rate 3 all six. In two passes the faces left out keep the other player's pass: player 1's reflection flickered [cause read; fix tested]. First fix: rate 3 (all six faces) in every pass, which cost **a third of a four player frame** [measured: 42.7 fps with, 59.4 without any reflections]: the faces are 1440 x 1440 here (the HD reflections mod), six drawings of the scenery per pass. Now (`reflections.cpp`) every player has a copy of the six faces (surfaces made with `CreateRenderTarget`, copied with `StretchRect` from the faces' surfaces: view 18-23 -> render target +0x60 -> surface +8): before a player's pass the faces the game is not going to draw this frame (Active byte +8 of each face's view, set by `UpdateCameras`) are copied in, after it the faces it drew are copied out, and the game updates at its own rate (the first pass of a player draws all six). `[options] reflection_copies=0` is the old way, `reflection_rate_four_players` (default 1) limits the rate with more than two players [tested: 57.6 fps, reflections look right by eye].
- **Shadows**: PC view ids differ from the console enum above 8: the cube-map views are 18-23 and the **shadow map views are 15 (player 1) and 16 (player 2)** (`eGetShadowMapView`, `eViews[15 + n]`, 0x919C70).
  `___eDisplayFrame` draws the player-1 shadow map each pass through `eRenderShadowPass(view 1)` → `eRenderShadowMap(view, ?, 0, 1)`, which puts view 15's camera around the camera of the view it is given (after
  the swap: the pass's player) and always uses shadow map 0 [tested with `[log] shadows=1`: drawn twice per frame, around each player]. **But the scenery for the shadow map is picked earlier** (`eStartFrameCulling`
  at the top of `___eDisplayFrame`, view 15, flags 0x4100) from view 15's camera as the last shadow map left it: in two passes that is the other player's. Symptom: shadows near a player pop out as the other
  player drives away (distance-based, some remain). Fix: view 15 gets a second camera object and PlatInfo (copies of its static ones; cameras are static 0x2C0 apart, view 1 at 0x986870, view 2 at 0x986B30; PlatInfos are `GimmeMyViewPlatInfo(id)` = 0x984130 + id*0x1A0) swapped in for the second pass, as a pair (camera alone made it worse: shadows behind player 1 vanished too) , so each pass starts with its own player's shadow camera from
  the previous frame [cause read + symptom matches; fix untested]. **View 16 has no camera (null): swapping with it crashes in `Camera::SetCameraMatrix`** [tested]. Gate in front of the shadow pass: `[0x901830] > 0` and `flt_8FAE68 >= flt_8FAE50` (meaning unknown).
- **Scenery draw table** [read; the vanishing shadows fix is untested]: each `___eDisplayFrame` call culls the scenery of every *active* view with an enabled cull job (views 1-4, the env maps, the shadow map view, last)
  into one table of draw entries (`DoCulling` 0x731B80: 0x994368..0x9A2DC8, about 3,700 entries, filled in job order). The game only draws view 1 per call, but in split screen view 2 is active too, so it is culled twice per frame for
  nothing, which can fill the table before the shadow map's job (last in the order): whole areas of shadow casters vanish (seen: shadows just behind the car, with or without the shadow camera fix, so not our regression).
  Switching view 2 off for the two passes (so it is not culled for nothing) **did not fix the vanishing shadows** behind the car and was removed (seen with every fix on and off: not our regression; whether the single player game has it is unchecked).
  Also tried without effect: pre-culler off (`PrecullerMode` 0x903160 = 0), the scenery detail patch below. Not tried: the shadow map's extent / fade (the shadow camera sits at the chase camera + sun direction * `[0x8FAEB8]`, looking at the chase camera position).
- **Scenery detail by view mode** [read; effect untested]: `ScenerySectionHeader::DrawAScenery` (0x729120) turns a pixel size into a model. In view modes >= 3 (`cmp eax,3; jl` at 0x729280) only objects over 22 px are
  drawn, always with the low detail model (`pModel[2]`); in one view over 17 px with the model the size calls for. Shadow casters go through the same test. Patched to the one view rule (`[options] cull_small_objects=0`).
- Streaming: `UpdateCameraMovers` 0x47C880 gives the track streamer (0x9AA9D0) a position for each **active** view (`PredictStreamingPosition` 0x7238D0); with view 2 active the world around
  player 2 loads natively. The streamer has two positions (entries of 0x64 at +0xC0) and a split screen flag (+0xB0, from `InitRegion` 0x72C070) under which it keeps both sets of sections.
- Seen/expected: effects updated in `___eDisplayFrame` (rain) run twice per frame; motion blur could
  blend the two pictures (not seen); shadows pop in oddly (maybe an old streaming issue).

## HUD and minimap
- Split screen makes two HUDs (`FEngHud` 0x5A6600): type 3 `HUD_Player1.fng` (player number 0) and type 4 `HUD_Player2.fng` (1) [tested: log]. The files are in `GLOBAL/InGameSplitScreen.bun` (JDLZ chunks, 0x30210).
  Only `HUD_Player1.fng` has the minimap objects (TRACK_MAP, the markers, ...); the `Minimap` is made in `FEngHud`'s constructor for types 1 and 3. Console design: one minimap at (-221, 0) in FEng coordinates
  (origin screen centre, 640 x 480), on the line between the halves, centred on player 1, player 2 as a second marker [tested].
- **The decomp's struct layouts do not match the PC exe** for these classes: `HudElement` is 0x30 bytes (object list +8, package name +0x10, mask +0x18, features +0x20), so every `Minimap` member is the decomp's offset + 8
  (map layout +0x38, own marker +0x90, other player's marker +0x94, default position +0x9C, map centre +0xB8), size 0x338, made with `malloc`; `FEngHud`: type +0x20, minimap +0x320; `FEPackage` object list head +0x4C;
  `FEGroup` first child +0x64 (matches); `FEObject` up to +0x5C matches. Virtual tables of the FEObject family: entry 0 deleting destructor, entry 1 `Clone` [read, tested].
- `Minimap::Update(player)` centres on the player it is given, north up in split screen. `UpdatePlayer2Element` draws the *last entry of the local player list* (0x92D87C, count 0x92D884) as the second marker.
  The map picture comes from `ChoppedMiniMapManager::UncompressMaps` (9 tile slots): it unloads every tile not in the list it is given, so two minimaps need one list with both sets.
  The Minimap places markers and icons itself, in absolute screen coordinates around its map centre (`UpdateElementArt`); only the map picture group's position is derived (default - displacement, every frame).
- `FEObject::Clone` (vtable entry 1) copies the scripts and responses but **not the object's data** (`pData`: colour, position, size - zeroed, so the clone is invisible) nor a multi image's texture fields, and it gives new GUIDs
  [read: the copy constructor 0x5C31A0 zero-fills; tested: clones with zero data were invisible]. Only images, groups and multi images (no pointers in their data) are copied by hand.
- **A clone plays its scripts from the start, which sets the position the object was made with**: a shift applied to a clone's data is lost on the next package update [tested: the clone of the ring / backdrop group stayed at (0, 0) while
  the original, whose scripts had finished, kept its shift]. The map picture group is exempt (set every frame); the others are put back every frame.
- **Widescreen** [read from a dump of both minimaps]: the widescreen fix posts `WIDESCREENMODE` 0x62ED04EC (`FEngHud::SetWideScreenMode` 0x5696C0, profile video setting +0x34 against the HUD's +0x330) once, to HUD_Player1.fng, whose scripts move the group 1603009e of the backdrop by -64; the clone in HUD_Player2.fng stays at 0, so player 2's black circle sat to the right of its minimap. `minimap.cpp` copies the originals' x to the shifted clones and their children every frame (not the map picture, which the minimap places itself) [tested].
- **Player 1's right-hand HUD** [read from a trace of the first frames]: `HUD_Player1.fng` has two groups for it, `2fe4ff9c` and `5d0101f1` (same children, both x 209), `HUD_Player2.fng` only `5d0101f1`. The widescreen fix moves `5d0101f1` by its offset (273 at 16:10), the layout's WIDESCREENMODE script moves `2fe4ff9c` by 120 on the second frame (329: clipped at 16:10, whose edge is 384). `minimap.cpp` puts `2fe4ff9c` where `5d0101f1` is when that has been moved [tested].
- **Video settings applied in the game** [screenshots; tested]: the widescreen fix's resolution event sets a flag, and the next `FEngHud::SetWideScreenMode` (called from `FEngHud::Update`) makes it work the offset out again, apparently from the window's size and not the game's (16:9 against 16:10), post the widescreen message to player 1's HUD again and call its own `AdjustForWidescreen` directly (not through the game's function, so not through our hook) on player 1's minimap. Player 1's right side and both minimaps (the copy follows the original) ended up further out; player 2's right side is never touched. Nothing is prevented: `settle_layout` in `minimap.cpp` records the x of both minimaps' members (+184 and the five children the fix moves), of player 1's groups 1603009e and 5d0101f1 and of every object the second minimap copies, 120 updates into the race, and `restore_layout` puts them back whenever they change (log: `hud: N positions had been moved by another mod's layout; put back`), unless the back buffer's size changed: then the layout settles again. Tried first and dropped: restoring each minimap's positions before the fix sees them, and ordering the two calls so the fix's one-minimap cache stays right (the direct call bypasses the hook).
- The minimap's circular backdrop is a black 128 x 128 image (hash 7af9160b) in the ring group (`TRACKMAPTARGETRING`, 382d2fc9) under the map picture. `HUD_Player2.fng` has an unrelated group with the same hash 157c5b37 at (-226, 7).
- FEng colours are 0xAARRGGBB (ints b, g, r, a in `FEObjData`); an object with alpha 0 is not drawn.
- **Built in `minimap.cpp`** [tested]: when player 2's HUD is made, the top level objects of `HUD_Player1.fng` that contain what the Minimap registered are cloned into `HUD_Player2.fng`; everything but the group holding the markers is moved
  +-120 (`kMinimapOffset` in `minimap.cpp`; the map picture, ring and backdrop); a second `Minimap` is built on the clones and shown / updated from player 2's `FEngHud::Update`; each minimap's second marker is the other player (hooked
  `UpdatePlayer2Element`); the markers are orange (player 1) and blue (player 2); the tile list passed to `UncompressMaps` is the union of both minimaps'; `AdjustForWidescreen` is repeated on the second. Not done: the rest of player 2's HUD
  is as the console has it (speedometer bottom right).
- **Per player On / Off** [built in `minimap_option.cpp`, Options > Player > Minimap; not run yet]: `FEngHud::DetermineHudFeatures` is hooked and the minimap bit (0x10000) and the heat meter's (0x4000: the flame and the ring around the minimap; the game sets and clears both together) are cleared for the player whose option is off (the HUD's type +0x20: 4 = player 2, any other = player 1); `update_visibility` calls the function through its address, so the second minimap follows. The game's own minimap setting, `RacingMiniMapMode` / `ExploringMiniMapMode` of the gameplay settings (2 = off, read in that function), is not per player.
- **Minimap visibility on pause** [tested]: `FEngHud::DetermineHudFeatures` 0x57CA60 makes all HUD hide on pause (checks `FEManager::IsPaused()` and whether `Pause_Main.fng` is pushed, no per-player case: decomp
  `FEPkg_Hud.cpp`), called from `FEngHud::Update` 0x58CA30, which then `HudElement::Toggle`s (0x5793F0) whatever that hud owns. Player 2's clone minimap (`g_b`) isn't owned by `FEngHud`, so `minimap.cpp` calls the
  same two functions itself to mirror the native path - but from `events::on_frame` (the `eDisplayFrame` hook), not `FEngHud::Update`: that does not run at all while paused, so a hook on it never sees the
  pause/unpause edge.

## Press Start and players
`FEngMapJoyParamToJoyport` 0x572FF0 (bit 0..3 to port 0..3, else -1): every FE press on PC is port 0, so the Press Start screen cannot tell devices apart. `uiQRPressStart` screen:
START_RELEASED 0xEBFCDA65, player number at screen `+0x2C`, `NotificationMessage` 0x7A3F20, `CreateQRPressStart` 0x570C60. The keyboard's Start is Space (Enter is Accept, ignored).
`players.cpp` ignores the game's own Start messages (which device ends in one depends on the bindings: Start on a pad is FE_ACTION_START = button 9 by default) and tells the screen itself: it reads
the XInput slots and the keyboard every frame and, when a controller lets go of Start or Enter / numpad Enter / Space is let go, sends START_RELEASED to the screen and gives that device to the player. Per race: player 1's vehicle takes its input from player 1's
device alone (`vehicle_source`, see input-system.md), player 2 reads the extra device; all devices drive every menu throughout (pause, Controls, car select); after the race (view mode leaves 3) every
device drives the vehicle again.

## More than 2 players: the menu flow (`player_count.cpp`, `more_players.cpp`; `[options] more_players=1`)
- **Race options row** [tested]: `UIQRTrackOptions` (`Track_Options.fng`, constructor 0x7BF6C0) builds its rows in `Setup` 0x7BA7C0 (a toggle widget per row, `AddToggleOption` 0x588570; split screen leaves out traffic, opponents, AI skill, catch up), called from one place, 0x7BF73D. **Redux v3 already redirects that call** (it went to 0x7BE454C0, a plugin's function), so hooking `Setup` with MinHook was never reached [tested]: `nfsmw::chain_call` (`common/patch.h`) reads where a call goes now, redirects it to ours and ours calls the old target. Use it for any game call another mod may also change; `redirect_call` is the strict version. The row is built like `nfsmw_custom_menus`' rows: `FEToggleWidget` constructor 0x589300 (0x5C bytes; we allocate 0xB0), PODriveCam's table 0x89C048 with slot 0 = FEToggleWidget's deleting destructor 0x589370, slot 1 `Act(package, pad message)`, slot 3 `Draw`, slot 14 blinks the arrow; label and value are language hashes (registered with `host->register_text`, so no custom menus = no row; until 2026-10-26 `register_text` strings only reached the game's language table when the Controls screen refreshed, so a mod with no Controls rows saw the layout's placeholders `option_name` / `option_data`: `controls_rows::apply` and `retranslate` now add them too) [tested: the row reads "Players  4" with its arrows]. It comes after the game's own rows: with Circuit that is the third (Direction, Laps, Players).
- **Press Start / Car Select know players 0 and 1 only** [read]: `uiQRPressStart` (`iPlayerNum` = the screen argument; its Back goes to Car_Select(0) or Track_Options), `UIQRCarSelect` (`iPlayerNum` = argument & 0xFF indexes `GetPlayerCarStable`, `GetPlayerSettings`, the quick race settings' selected car; after player 0 it goes to PressStart(1), after player 1 it commits). Per-player data is in arrays of 2 (`CurrentUserProfiles[2]` at FEDatabase +0x10, `PlayerJoyports[2]`, `ThePlayerSettings[2]`, `TheRaceParameters.PlayerJoyports[2]` / `PlayerStartPosition[2]`), so players 3 and 4 run the same two screens a second time instead of getting screens of their own.
- **Where the race starts** [read, tested]: player 1's car is `SelectedCar[0]` of the "all types" quick race settings (`GetQuickRaceSettings(11)` 0x56DBE0; PC `RaceSettings` is 0x18 bytes, `SelectedCar` at +0x10, not the decomp's +0x1C). Player 2's profile is a temporary one: the commit function (0x7A3AF0, called with `UIQRCarSelect`'s accept) calls `DeleteMultiplayerProfile(1)` 0x58FFA0, which copies player 2's car name to FEDatabase +0x470 and a malloc'd copy of its `FECustomizationRecord` (0x198 bytes) to +0x46C, then `RaceStarter::StartRace` 0x57ECA0 (the call at 0x7A3B09 is redirected). `QuickGame::CreateCars` reads those two for player 2 (and frees the copy).
- **The second round** [tested]: with 4 players the call is held back after the first round: the picks (player 1's car handle, player 2's name and customization, both devices from `players.cpp`) go into a table, `PressStart.fng` is queued for player 0 again (its text is rewritten to "Player 3" / "Player 4"), and after the second round the first round's picks and devices are put back and `StartRace` is called: the race has players 1 and 2. The picks of 3 and 4 are in `g_picks[2..3]` for the code that will make them. Car Select's own "Player 1 / 2" label is not changed. 3 players is not offered: after player 3 the game's car select goes to Press Start for the next player by itself.
- **Players 3 and 4 in the race** [tested: 4 cars stand at 4 places, 2 clean views and HUDs, no crash]: `QuickGame::CreatePlayers` 0x6F2700 (two `LocalPlayer` entities: controller port, settings slot, render port 1 / 2; `IPlayer` virtual table: +4 `GetSimable`, +8 `IsLocal`, +0xC `GetPosition`, +0x18 `SetSettings`, +0x20 `GetHud`, +0x28 `SetRenderPort`, +0x2C `GetRenderPort`, +0x30 `SetControllerPort`) and `CreateCars` 0x6F47A0 are each called once, from `QuickGame::OnBeginState` (0x6F4EDA, 0x6F4EE5). The local player list is an array at 0x92D87C with its count at 0x92D884 (`IPlayer::GetList(PLAYER_LOCAL)`). `CreateCars` makes a `VehicleParams` (0x30 bytes: a `Sim::Param` {type crc, name crc 0xA6B47FAC, pointer to itself, pad}, then driver class, car key from `Attrib::StringToKey(lower case name)`, direction, position, customization, vehicle cache, performance match, flags) for the first car and, in split screen, for the second, with the position of the second a fixed step from the first, and each is created by the `Sim::Param` factory and bound to the first and the LAST entry of the local list (a vehicle bound to the wrong player left that player's `GetSimable()` null and crashed `SimSystem::PauseInput` 0x6F0FB0 and the HUD code: they call it for every local player). Extras: `CreatePlayers` again, then `CreateCars` again with the list swapped to players 3 and 4 and the picks of round 2 where it reads them, then the list shrinks back to 2 players. **Local players need a HUD and a render port that is a view** (`FEngHud::DetermineHudFeatures` 0x57CA60 indexes the view table by it: -1 crashed; HUD `LocalPlayer::SetHud` 0x6E99C0 makes `FEngHud` of type 3 / 4 = package `HUD_Player1.fng` / `HUD_Player2.fng`, so two more players meant two more copies of those packages on the same views, drawn over the real ones; a null HUD crashes 0x631144), so players 3 and 4 are left out of the local list instead (they are still in the all-players list, which `QuickGame::OnQueryVehicleCache` uses to keep their vehicles). The race then counts their cars as racers: players 1 and 2 are placed 3rd and 4th. Not done: a car pool for four cars (`CarLoaderPoolSizes[1]` of `RegionLoader::BeginLoading`: the default cars ran it out of room with two), their race status (positions, finishing).
- **Four views** [tested: 2x2 picture, four different viewpoints]: `split_view.cpp` `four_view_frame`. Every pass is the whole picture shrunk (StretchRect, linear) into its quadrant of the canvas: a quadrant has the screen's aspect, so no band is cropped. Player 1's pass is the game's own; player 2's trades views 1 and 2 as before; players 3 and 4 put **a camera of our own into view 2's slot** and then trade as for player 2. The game has no camera for them: `CameraAI::Update` 0x480E40 loops over the view ids 1 and 2 only, finds the local player with that render port and makes a `CameraAI::Director` (0x2C8 bytes, 0x480D20) for it, so extra views need our own. The camera: a copy of view 2's `Camera` (0x2C0 bytes) and PlatInfo (0x1A0), a look-at matrix behind the car (`eCreateLookAtMatrix` 0x6CF0A0, cdecl: matrix, eye, target, up; 6 m behind, 2 m up, looking 1.2 m above the car), `Camera::SetCameraMatrix` 0x4700D0 (thiscall: matrix, time; **the time must be the real time since the last call**: with 0 the two extra views were blurred, whatever the other players did [tested]; the camera keeps the last matrix and the time, and the blur works out the speed from them), then the game's `eView::SetupPerView` 0x6CF400 (matrices from the camera and the render target) and `eView::SetupWorldLightContext` 0x5029F0 (thiscall on the view: lighting from its camera; it allocates from the frame pool, so run after the pool was put back) for view 2. **Render space is the simulation's with (x, y, z) -> (z, -x, y)** (`eSwizzleWorldVector`, `bConvertFromBond`). The car's state: `IPlayer::GetSimable` (+4) -> `ISimable` +0x54 `GetRigidBody` -> `IRigidBody` +0x20 `GetPosition`, +0x34 `GetForwardVector(Vector3&)`, +0x3C `GetUpVector` (the decomp's slot order plus one for the base interface). Each pass has its own copy of the shadow view's camera and PlatInfo (see Shadows). **Streaming** [tested by driving: the world stays loaded around the parked cars]: `TrackStreamer` (0x9AA9D0) has `StreamingPositionEntries[2]` (0x64 bytes each from +0xC0, with fields right behind them and about a dozen loops over exactly two in its code), so it cannot get more places. `Camera::UpdateAll` 0x480C16 calls `UpdateCameraMovers` 0x47C880, which gives each *active view with a camera mover* a place with `TrackStreamer::PredictStreamingPosition` 0x7238D0 (thiscall: slot, position, velocity, direction, flag; position in the render space's x, y plane): views 1 and 2 only. `extra_streaming.cpp` redirects that call and, with four cars, picks the two of them that keep every car nearest to one place (two-centre of four, in the plane of the track) and writes those into the two entries (a player 1 or 2 keeps the game's own entry, an extra player gets one from `PredictStreamingPosition`). Cars further apart than the range of the two places will still pop in. **Reflections** [tested by eye]: `UpdateEnvironmentMapCameras` 0x756060 centres the car cube map on the car the first camera mover of view 1 follows (else on the first local player's car) and calls `eEnvMap::UpdateCameras(viewer position, cube map centre)` 0x6DA350 (call at 0x75611D); in the passes of players 3 and 4 that car is player 2, so `split_view.cpp` redirects that call and moves the centre by the difference between their car and player 2's. (`IRigidBody::SetPosition` of a car whose driver is not there does not stick: the car was back near the start a few seconds later.) Not done: the cameras of players 3 and 4 are rigid (no smoothing, no camera settings).
- **Where the time of a four player frame goes** [measured with `profile` and `[options] frame_timing`, 1280x720 windowed, Redux v3]: each pass costs 5.5 ms of CPU and about as much of GPU (the GPU waits for the CPU): the game thread's samples were 28% d3d9.dll, 23% d3dx9_43.dll (the effects' state), 24% speed.exe, 9% ntdll, 5% msvcrt, so the cost is **draw calls**, in `sub_6E0200` (the per object submission) and what it calls. A pixel limit of 4 times the game's (`eView::PixelMinSize`, +0x24, culls small objects) made no difference, so object count is not what costs; the cube map faces did (above). The stock scenery rule (22 px, lowest detail) is used for four players: `fixes::use_one_view_scenery_rule`.
- **HUD for four players** [tested]: `hud_views.cpp`, `hud_players.cpp`, `hud_packages.cpp`. **FEng draws the HUD per package** (`cFEngGameInterface::BeginPackageRendering` 0x5166A0 / `EndPackageRendering` 0x516710, `package+0xC` the name), the polygons in FE units (640 x 480) which `eViewPlatInterface::Render` 0x6D1260 turns into -1..1 (x/320 - 1, -(y/240 - 1)) and draws at once, so **the D3D viewport decides where a package lands**: `hud_views.cpp` sets it to a player's cell for that player's HUD package and the HUD (made for the whole screen) is drawn scaled into it. The HUDs of a split screen race are made for the top half of the screen (HUD_Player1.fng: minimap at the half's lower edge, speedometer at its bottom), which put the speedometer in the middle of a cell: the four `fsub dword ptr [0x89096C]` after `fmul [0x8AF9A0]` in that function (0x6D12D9, 0x6D1329, 0x6D13AC, 0x6D1432: the 1.0 of the y) read a variable of ours (0 while a HUD is drawn), which draws the HUD one viewport lower, so the half becomes the bottom of the cell. The minimap sits on the half's lower edge, so `minimap::place` lifts it by 75 FE units (the objects the minimap registered, except the marker group, and the minimap's map centre y +0xBC, default y +0xA0; pinned every frame, as the layout's scripts put them back).
  **Packages**: the HUD finds its objects by the package's name, so each HUD needs a package of its own. `hud_packages.cpp` copies one under another name (`HUD_PlayerB.fng` ...: same length): the game's packages are `FEPackageData` (0x38 bytes: chunk at +0x18) in the `FEPackageManager` list, made by `LoaderFEngPackage` 0x585AA0 from the bun's chunks; a package of a bun is a compressed chunk (id 0x30210: name hash, JDLZ block with the uncompressed size at +8; `LZDecompress` 0x650350 (cdecl, source, destination)), the uncompressed form is id 0x30203 + size + the data (`FEng` chunk, `PkHd` header chunk: short name at data +0x28, then the file name; the name is replaced in both). The copy is handed to `LoaderFEngPackage`. **Every HUD is a copy of HUD_Player1.fng** (it has the minimap objects): player 1 keeps the original, `FEngHud`'s constructor gets the copy's name for the type 4 HUDs (`events::on_hud_construct`: type 4 never loads textures, so the resource manager is not asked four times), the Minimap is made on the copy (`Minimap::Minimap` 0x59D500 (thiscall: memory 0x338 from `malloc` 0x7C66D0, package, player number)) and stored in the HUD's minimap slot (`FEngHud` +0x320), where the HUD's update, `SetHudFeatures` and the destructor use it. Players 3 and 4 are not in the local player list, so the game makes no HUD for them: `LocalPlayer::SetHud` (IPlayer vtable +0x24) is called on them from the frame hook once the HUDs of 1 and 2 exist (the HUD of a type 4 gets a copy again; the entity's HUD task updates it). `FEngHud::DetermineHudFeatures` looks at the camera mover of the view of the player's render port and shows nothing without a `CM_DRIVE_CUBIC` mover, so the extra players get a render port (1 or 2: a view with a mover) only while their HUD updates (`more_players::lend_view`). `FEngHud` fields (PC): type +0x20, countdown element +0x318, minimap +0x320. **The 3, 2, 1, Go!** is an element of the HUD (`Countdown`: `BeginCountdown` 0x567F10 is called for the HUDs of the local players only, so the hook calls it for the others, with the same pointer offset into the element; players whose HUD is made later start late).
  **Minimaps**: `ChoppedMiniMapManager::UncompressMaps` has 9 tile slots and unloads every tile not in its list; the lists of all minimaps are merged with each tile once (four minimaps asking for different lists overflowed the allocator: a crash in `bFree` / the pool). Markers: `minimap::set_markers`: own marker colour per player (orange, blue, green, purple); the others are shown with the minimap's second marker (`PLAYERCARINDICATOR2`, +0x94, driven by `Minimap::UpdatePlayer2Element`, which draws the last local player: hooked to draw the first other player) and, for the rest, **copies of that marker** (the HUD_Player1 layout has none of the AI racers' markers (`MMICON_AIRACER_n`, Minimap +0xF0) that `UpdateAiRacerElements` would draw): `FEObject::Clone` (vtable 1) + `finish_clone`, added to the marker's group with `FEGroup::AddObject` 0x5B5420, positioned with `Minimap::UpdateElementArt` 0x5675D0 (thiscall: position, direction (2 floats each), object, pulse) after each `Minimap::Update`, hidden when the own marker is.
- **HUD corners and HUD Scale** [tested; layout and scaling seen in screenshots]: the object tree of `HUD_Player1.fng` (`[options] dump_hud=1` logs it, `dump:` lines): the right side is two groups, `2fe4ff9c` (209, -176) with `5c7a5c8a` below it, which holds the race information (`b1c5ed0d`, absolute y about -192: the top right) and the speedometer cluster (`5164d4ea`, `941fff09`, `87c38e97`, `edfb6d37`: absolute y -114 to -22: the bottom right), and `5d0101f1` (the same children, for other layouts); the left side is the minimap (`0f365871`, `157c5b37` > `1603009e` > `382d2fc9` > `7af9160b` the black disc, markers in `00a1a862`, whose children `dd9ef5ff` / `917db611` are the two markers); top centre are the countdown (`3d2aed05` > `32a7a521` "321_GO", y -204) and the messages (`e0ba07ec`); `92d6630d` is the 1200 x 4 line between the two halves. `hud_views.cpp` hooks `cFEngGameInterface::RenderObject` 0x516630 (every object, drawn at once) and gives each object a viewport of its own: `classify` sorts every leaf object by its absolute place (own plus its groups' positions, FE units, origin at the screen's centre): x < -100 left (always the bottom: the minimap), x > 100 right, else the middle; y < -150 top, else bottom.
