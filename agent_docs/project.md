# Project: layout, build, test setup

## Game installs
Mods and scripts never hard-code an install location: always pass the game directory as an argument. The hooks check the first 7 bytes of each function before patching it, so the same addresses install on every speed.exe 1.3 build, whatever its size or hash.
- `python Mods/set_mods.py --mode all|ours|none --game <dir> [--only <mods>]` picks which `.asi` load (the rest wait in `scripts_disabled/`) and builds the texture packs. It first closes a game running from that install (`--keep-running` skips that): overwriting a loaded `.asi` crashes the game.

## Our mods (`Mods/`, one folder each, built together)
`custom_menus` (Options menu framework), `camera_settings` (camera presets, Options > Camera), `controller_support` (controller input, bindings per controller, camera look, rumble, button icons; namespaces are `pad::`), `split_screen_support`, `dev_tools` (start-up and diagnostic tools), `custom_menus/example_options_page` (an example plugin with a dummy Options page, built but not in `set_mods.py`), `common/` (header-only: log file, `hooks.h`, language table merge, XInput, the APIs between mods). Each mod folder holds its `ReadMe.md` (for players), its `.ini` (every setting), `src/` (all `.cpp` and `.h`) and data folders (`translations/`, `buttons/`, icon PNGs); how to work on them is in `.claude/skills/nfsmw-modding`, what we know about the game in `agent_docs/`.
- Everything our mods write or ship lives in `<game>/scripts/mets_mods/` (`nfsmw::data_file()`): `.ini`, `.log`, texture packs. Uninstall = delete the `.asi` files and that folder.
- `common/hooks.h` `install_hooks`: checks the first 7 bytes (a function that starts with a jump, i.e. another mod's hook, is hooked on top of it; any other difference skips the hook), optional `[hooks]` skip list in the mod's ini, required hooks are all-or-nothing; log lines read "hooks installed - <group>: n of m". **Two plugins cannot hook the same function**, so code that builds a screen sits next to the hooks that build it (that is why the Options menu is its own mod).
- Icons: `<mod>/OPTIONS_*.png` become `<mod>.tpk` (`Tools/tpk_build.py`).

## Build
Windows (MSYS2 MINGW32): `cd Mods && cmake -S . -B build -G "MinGW Makefiles" && cmake --build build` with `C:\msys64\mingw32\bin` first on PATH (installed 2026-10-06 with `winget install MSYS2.MSYS2`, then `pacman -S mingw-w64-i686-gcc mingw-w64-i686-cmake mingw-w64-i686-make`; not on the system PATH; uninstall with `winget uninstall MSYS2.MSYS2` and delete `C:\msys64`).

Linux (cross-compile, installed 2026-10-13 with `dnf install mingw32-gcc-c++ mingw32-binutils mingw32-crt mingw32-headers mingw32-filesystem mingw32-winpthreads`): `cd Mods && cmake -S . -B build -DCMAKE_TOOLCHAIN_FILE=../Tools/nfsmw-2005-sdk/cmake/nfsmw-toolchain-mingw-i686.cmake && cmake --build build`. The game itself runs through Steam Proton Experimental; only the build is cross-compiled, nothing runs under Linux natively.

Releases: `.github/workflows/release.yml` builds the mods (with the same cross-compile setup as on Linux above) when a tag `v*` is pushed or by hand from the Actions tab (typing the version, which makes the tag), and publishes `Mods/package_release.py`'s zip (the four player mods, their `.ini`, texture packs and translations in the game's `scripts/` layout; not dev_tools or the example) as a GitHub release [not run yet].

Either way `build/` is disposable. The runtime must be linked statically (`Mods/CMakeLists.txt`), or the ASI loader fails with "Error 126" (missing `libgcc_s_dw2-1.dll`).

## Testing the game
- The `.asi` cannot be replaced while the game runs. Windows: a hung `speed.exe` that `taskkill` cannot kill dies with `Get-CimInstance Win32_Process -Filter "Name='speed.exe'" | Invoke-CimMethod -MethodName Terminate`. Linux, running under Steam Proton Experimental: kill the game's own process by PID (`pgrep -f '(^Z:.*|^\./)speed\.exe$'`); `pkill -f speed.exe` also matches and kills the shell running it.
- Linux: launching without Steam, and backtraces. `cd <install> && STEAM_COMPAT_DATA_PATH=~/.local/share/Steam/steamapps/compatdata/<id> STEAM_COMPAT_CLIENT_INSTALL_PATH=~/.local/share/Steam "<Proton - Experimental>/proton" run ./speed.exe` (`<id>`: the non-Steam shortcut's compatdata folder). Backtraces of a running game: `WINEPREFIX=<compatdata>/pfx WINEDLLPATH="<proton>/files/lib/wine:<proton>/files/lib64/wine" "<proton>/files/bin/wine" winedbg --command "bt all"` (works on a Steam-launched game too); map `.asi` offsets with `i686-w64-mingw32-nm -n` on `Mods/build/*.dll` (offset + ImageBase).
- **Black screen at start-up, no frame drawn** [tested]: the main thread hangs in DirectSound's start-up (`EAXSND8Wrapper::Initialize` -> dsound -> Wine `mmdevapi`) when PipeWire has no real output - cards' profiles "off", only "Dummy Output", no default sink (`pactl info`, `wpctl status`). Not the mods: it happens with none loaded. `systemctl --user restart wireplumber pipewire pipewire-pulse` brought the outputs back and the game booted every time. How to tell: the boot flow has no current screen (`*0x91CF48` null or its screen unset) and `eFrameCounter` (0x982B78) / `RealTimeFrames` (0x8F82F4) do not advance. The other start-up stalls are the save-directory check waiting on a message (MemoryCard +0x14, see `menus-and-camera.md`) or never finishing. After a suspend/resume this is the usual cause (the audio stack comes back without outputs). `Tools/linux/restart-user-audio.sh` + `.service` fix it system-wide: a oneshot service ordered after the suspend/hibernate targets that, for each user with no real default sink, restarts WirePlumber (then the whole PipeWire stack). Install (root, from the repo root): `sudo install -m 755 Tools/linux/restart-user-audio.sh /usr/local/bin/restart-user-audio && sudo install -m 644 Tools/linux/restart-user-audio.service /etc/systemd/system/ && sudo restorecon -v /usr/local/bin/restart-user-audio /etc/systemd/system/restart-user-audio.service && sudo systemctl daemon-reload && sudo systemctl enable restart-user-audio.service`; log: `journalctl -t restart-user-audio`.
- On an install that is a bundle of mods with the widescreen fix, always keep the bundle's other mods on: without them the game renders no 3D and garbled text.
- Direct3D 9: patching the device's vtable gets reverted within ~13 frames on this install; hook the `d3d9.dll` function bodies with MinHook. The device pointer is `[0x982BDC]`.

## Reference sources (`Tools/`)
`nfsmw-2005-sdk` (submodule: headers the mods build against). Other reference clones are expected in `Tools/` but are not committed: [`nfsmw-decomp`](https://github.com/dbalatoni13/nfsmw) (`config/SPEED_EXE_1_3/symbols.json` = ~46k PC function names and addresses), `nfsmw-2005-re` (article repo with `tools/nfsmw-tool`) and, in `Tools/OtherMods/`, other people's mods: NFSMWExtraOptions (GPL-3.0; reference only) and the widescreen fix (MIT, e.g. `Controller.ixx`).
`Tools/build_xenon_effects.sh` builds the XenonEffects [fork by TorutheRedFox](https://github.com/TorutheRedFox/NFSMW_XenonEffects) (a C++ rewrite using EASTL that is newer and has more options than [the original](https://github.com/xan1242/NFSMW_XenonEffects), which has ~20 functions of MSVC inline assembly; the fork needs `eastl` pinned to 3.18.00, `eabase`, `eaassert` and the original's `includes/injector` and `includes/mINI`) on Linux (its project file expects NuGet packages that are not in the repo): three functions are MSVC inline assembly, which GCC cannot compile, so clang (target i686 MinGW, `-fms-extensions -fasm-blocks`) compiles copies of the sources without the BOM, non-ASCII comment characters and `ds:` prefixes, and MinGW's g++ links it. Output `Tools/OtherMods/build/NFSMW_XenonEffects.asi` (needs the speed.exe 1.3 with MD5 c0516b48...) [built, untested in game].
**Vault databases** (`attributes.bin`, `FE_ATTRIB.bin`, `gameplay.bin` and its `gameplay.lzc` wrapper in `GLOBAL`, as opposed to the BIN/BUN chunk containers) are edited with [Attribulator](https://github.com/NFSTools/Attribulator). The setup, the workflow and the scripts for comparing and merging mods are documented in `Mods/overhaul_for_redux_v3/ReadMe.md`. Not in there: the Overhaul changes 2463 values and Redux v3 changes 1667 and adds 1241 records; Rework v4 and the Overhaul conflict in 740 values (522 to different values, mostly race definitions), so they were not merged; Rework's `GLOBAL` does not unpack with stock VaultLib.Core 1.1.3, because 91 `helper*` records in `gameplay` name a parent collection (`helper`) that no vault defines.
Evaluated and removed (do not redo): [**Binarius** / Binary](https://github.com/nlgxzef/Binarius) edit BIN / BUN / LZC data (textures, strings, car parts) and its Most Wanted loader throws `VPAK Vault files are not supported` for the vault files; **NFS-VltEd** v4.6 is closed source, the only source is a [decompile](https://github.com/Sh2dow/NFS-Vlted-Recycled) with no licence, and Attribulator did the whole job.
Scripts: `re/re.py` (listing with names, cross references, `names.json` overlay), `tpk_list.py` / `tpk_export.py` / `tpk_build.py` (texture packs; `Exports/fe_textures/` is a gallery from the export), `attrib_hash.py`, `button_pack.py`, older `xref.py` / `xcalls.py` / `compare_names.py` / `check_addrs.py`.
- **Simulation speed** [read in the exe; `dev_tools/src/game_speed.cpp` written, not yet run]: `SimSystem` +0x24 is the speed (`Sim::GetSpeed` 0x6E8DC0; the game's slow motion sets it every frame through `ITimeManager::OnManageTime`), `SimSystem::UpdateFrame` 0x6F6CF0 makes the step `mTimeStep` (+0x1C) = `mScheduleStep` (+0x18) * speed at 0x6F6D94..0x6F6DA6, and the whole simulation takes its time from that step. Our dev tool multiplies the step by one more number there (a stub at 0x6F6DA0).
